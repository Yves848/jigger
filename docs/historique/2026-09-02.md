## 12:56 — Réalisé : le module pacman / yay

**Demande :** ajouter à jigger le module pacman / yay, cette machine étant sous Arch
(Omarchy).

**Actions :**
- Quatre arbitrages soumis avant d'écrire une ligne, tous tranchés sur la recommandation :
  périmètre complet (complétion + façade + prompt), yay seul pilote, l'AUR au catalogue de
  yay, et spec + ADR avant le code.
- Environnement mesuré avant de concevoir : `pacman -Sl` 166 ms / 15 604 lignes,
  `pacman -Qq` 10 ms, `readdir` de `/var/lib/pacman/local` sous la milliseconde,
  `checkupdates` 510 ms (réseau), `yay -Slq aur` 799 ms / 118 582 noms.
- Conception (`docs/specs/2026-09-02-pacman-design.md`) et ADR-0007 rédigés, puis le
  module : `internal/pacman` (7 fichiers, 4 de test), le câblage dans `managers`, `pm`,
  `ui`, `prompt`, `i18n` et `main.go`, le greffon zsh, deux segments de prompt et les
  quatre documents d'accueil.
- Go n'était pas installé sur la machine : `mise use -g go@latest` (1.27.0) après accord,
  ce qui a permis de compiler, tester et **éprouver le binaire en vrai** plutôt que de
  livrer du code non compilé.

**Fichiers :**
- `internal/pacman/` — le module : deux fournisseurs, catalogue à deux étages, verbes,
  analyseurs, état du prompt.
- `internal/complete/complete.go` — casse des sous-commandes, `subBrut` pour le titre.
- `internal/pm/pm.go` — `BadgeRepo`, `BadgeAUR`, `NewCatalogDe`.
- `internal/managers/`, `internal/ui/frame.go`, `internal/prompt/status.go`,
  `internal/i18n/catalogue.go`, `main.go` — câblage.
- `shell/jigger.plugin.zsh` — `JIGGER_COMMANDS`, détection des opérations mutantes,
  nommage des variables de prompt.
- `shell/oh-my-posh/pacman.segment.json`, `shell/starship/pacman.toml` — blocs de prompt.
- `docs/specs/2026-09-02-pacman-design.md`, `docs/adr/0007-pacman-lit-yay-pilote.md`,
  `docs/ameliorations.md` (A-16), les deux README, les deux getting-started, `CHANGELOG.md`.

**Décisions / notes :**
- **Les opérations de pacman sont des drapeaux**, et le moteur route sur
  `HasPrefix(word, "-")` : elles tombaient du mauvais côté du test. Réglé **sans toucher au
  moteur** — le fournisseur déclare la même liste dans `Subcommands()` et dans
  `Options("")`. Deux asymétries préexistantes de `complete` sont sorties au passage : la
  branche des sous-commandes ne minusculait pas (contrairement à celle des options), et le
  cadre annonçait `pacman -rns`, qui n'est pas une commande valide.
- **ADR-0007 — pacman lit, yay pilote.** Les deux mots de commande donnent sur une seule
  base alpm, situation inédite ici : `Router` lance tous les gestionnaires capables d'un
  verbe sans nom à résoudre, donc `jg list` aurait tout listé deux fois et `jg install fd`
  aurait ouvert le popup de désambiguïsation à chaque installation.
- **Le budget de la frappe a failli être crevé.** La première rédaction fusionnait le
  catalogue à chaque `render` : 45 ms, pour un budget déclaré de « quelques ms »
  (`complete_test.go:332`). `render` étant appelé en substitution de commande dans le
  widget zle, c'est de la latence de frappe directe. Le coût a été bissecté au banc
  (lecture 10 ms, allocation 1,8, boucle dépôts 2,0, boucle AUR 8,3, tri 3,0) avant de
  déplacer la fusion dans `warm`. Résultat : `yay` 70 → **28 ms**, `pacman` 13 → **7 ms**,
  `warm --all` 1 058 → **710 ms**.
- **Le bloc de prompt exportait `JIGGER_BREW_*` en dur** : sur Arch, les chiffres de pacman
  sortaient sous un nom faux. Les noms se décident maintenant au chargement du greffon.
- Vérifié sur données réelles, pas seulement en test : `yay -S 1password` insère
  `omarchy/1password` (121 noms sont portés par un dépôt *et* l'AUR, presque tous du dépôt
  `omarchy`) ; `jg outdated` répond « nothing to report » en code 0 malgré le code 1 que
  pacman rend quand il ne trouve rien ; la détection des commandes mutantes du greffon a
  été éprouvée sur dix-neuf lignes, `git commit -m 'pacman -Syu'` compris.
- **Reste ouvert :** les 28 ms de `yay` sont la lecture de 2,1 Mo et le remplissage d'une
  table de 134 000 entrées. Les faire tomber encore demanderait un badge par défaut sur
  `pm.Catalog` — un changement du type partagé par les quatre gestionnaires pour une
  dizaine de millisecondes. Écarté sciemment, et noté dans la conception.
