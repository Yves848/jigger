# Internationalisation de jigger — conception

16 août 2026 — état : validé, prêt pour le plan d'implémentation

## Objet

Rendre jigger **multilingue**, et faire de l'**anglais sa langue de publication**.

Deux décisions distinctes, prises ensemble parce qu'elles se servent l'une l'autre :

- le binaire et les greffons apprennent à parler plusieurs langues, sur la recette déjà
  éprouvée dans Cocktails ;
- la documentation publiée — README, guide, CHANGELOG — passe en anglais, le français
  devenant une traduction maintenue à côté.

Le tout précède deux chantiers qui en dépendent : le **site de présentation** et la
**stratégie de diffusion**. Traduire d'abord, publier ensuite : l'inverse obligerait à tout
reprendre.

## Point de départ

jigger est en v0.8.0 : la façade multi-gestionnaires est en place, le guide de premiers pas
est écrit, la release est publiée et installée par le tap. **Tout est en français** — les
chaînes du binaire, les messages des greffons, la documentation, le code et ses
commentaires.

Le public visé, lui, ne l'est pas. Les utilisateurs et les contributeurs d'outils en ligne
de commande — Homebrew, winget, scoop, et les endroits où ce genre d'outil se fait
connaître — lisent l'anglais par défaut.

Cocktails, l'application graphique de la même suite, a déjà résolu ce problème :
`src/Cocktails/Localization/` tient quatre langues (EN, FR, ES, DE) dans un catalogue unique
`clé → [EN, FR, ES, DE]`, avec deux règles de repli et un code commenté en français. Ce
document reprend cette recette et l'adapte à un CLI.

## Décisions structurantes

Cinq choix arrêtés, dont tout le reste découle.

1. **L'anglais devient l'original, le français une traduction.** Y compris le CHANGELOG.
   Les documents de travail — ADR, specs, plans, journal, messages de commit, issues —
   restent en français.
2. **Le code et les commentaires restent en français**, comme dans la couche de
   localisation de Cocktails elle-même. Ce n'est pas une inconséquence : ce sont deux
   publics différents.
3. **EN et FR maintenant ; ES et DE le jour où quelqu'un peut les relire.** Une traduction
   que personne n'a relue se voit immédiatement dans les chaînes courtes d'un terminal, et
   personne ne la signale — on change d'outil. Ajouter une langue coûtera une constante et
   une colonne (cf. §2), et le repli sur l'anglais couvre les lignes encore vides : c'est
   une porte d'entrée toute trouvée pour un premier contributeur.
4. **Un catalogue unique dans le code**, une ligne par clé, toutes les langues côte à côte.
   Pas de fichiers de langue séparés : la dérive de clés devient structurellement
   impossible.
5. **La frontière humain / machine est explicite** et fait partie du contrat. Ce qu'un
   greffon ou un script analyse n'est jamais traduit.

## §1 — La frontière humain / machine

C'est la décision qui protège les greffons et les scripts des utilisateurs. Une chaîne
traduite par erreur casse une installation à distance, silencieusement.

### Traduit

| Surface | Exemples |
|---|---|
| Pied et chrome du popup | `insérer`, `exécuter`, `naviguer`, `parcourir`, `annuler`, `choisir`, `fermer`, `filtrer…` |
| États du popup | `aucun candidat`, `catalogue Homebrew en préparation…`, l'invite à taper une lettre |
| Messages de la façade | verbe inconnu, `inconnu de brew`, les deux messages `--pm`, `Proche :`, le rappel « paquet trop récent », `rien à signaler`, « connu de plusieurs gestionnaires » |
| En-têtes de tableaux | `PAQUET ACTUEL DISPO SOURCE PM` → `PACKAGE CURRENT AVAILABLE SOURCE PM` |
| Ligne d'usage et descriptions de drapeaux | `main.go` |
| Messages de chargement des greffons | binaire introuvable, version incompatible |

Les en-têtes de tableaux méritent leur justification : les traduire est sans danger
**parce que `--json` existe**. Qui veut analyser une sortie dispose d'une forme faite pour
ça, dont les clés ne bougent pas.

### Jamais traduit

| Surface | Pourquoi |
|---|---|
| La première ligne de `render` : `count=`, `sel=`, `exec=`, `left=` | les deux greffons la découpent à chaque frappe |
| Les clés JSON : `name`, `version`, `available`, `kind`, `source`, `pm` | contrat machine |
| Le vocabulaire du domaine : `install`, `--pm`, `brew`, `formula`, `cask`, `tap`, `bucket` | ce sont des noms propres de gestionnaires |
| Les erreurs d'invariant interne (« liaison sans Native, Build ni Direct ») | elles s'adressent au développeur ; elles restent en français avec le code |

## §2 — Le catalogue

Un paquet `internal/i18n`, deux fichiers :

- `catalogue.go` — la table, et rien d'autre ;
- `i18n.go` — la résolution de la langue et les deux fonctions d'accès.

```go
// [EN, FR] — l'anglais est l'original, le français la traduction.
var catalogue = map[string][nbLangues]string{
    "popup.insert":          {"insert", "insérer"},
    "popup.browse":          {"browse", "parcourir"},
    "facade.verbe_inconnu":  {"unknown verb", "verbe inconnu"},
    …
}
```

`nbLangues` vaut **2** à la livraison. **Un tableau de taille fixe, pas un slice** : c'est le
seul écart avec Cocktails, et il est délibéré. Le jour où l'espagnol arrive, `nbLangues`
passe à 3 et le compilateur désigne **chaque ligne** à compléter ; un slice laisserait
découvrir les trous à l'exécution, chez un utilisateur. La table ne porte donc jamais de
colonnes vides d'avance — c'est le compilateur, et non la discipline, qui tient le compte.

**Accès :**

```go
i18n.T("popup.insert")                        // chaîne simple
i18n.Tf("facade.pm_indispo", pm, disponibles) // avec paramètres
```

**Deux règles de repli**, reprises de Cocktails :

- **clé absente** → la clé est rendue telle quelle. Une chaîne oubliée saute aux yeux
  (`popup.insert` au lieu de `insert`) au lieu de laisser un trou.
- **traduction vide** → repli sur l'anglais. C'est ce qui permet de livrer des colonnes ES
  et DE vides sans rien casser.

**Nommage des clés** : par domaine, en minuscules, `popup.*`, `facade.*`, `cli.*`, `warm.*`.
Le préfixe dit où la chaîne s'affiche, ce qui rend une relecture de traduction possible sans
lire le code.

## §3 — La résolution de la langue

Dans cet ordre, premier trouvé l'emporte :

1. `JIGGER_LANG` — `en` ou `fr` aujourd'hui. L'échappatoire de l'utilisateur, et ce que
   **tous les tests** posent ;
2. `LC_ALL`, puis `LC_MESSAGES`, puis `LANG` — on garde ce qui précède `_` ou `.`
   (`fr_FR.UTF-8` → `fr`) ;
3. sous Windows, la culture utilisateur, par `GetUserDefaultLocaleName` — **aucune
   dépendance nouvelle**, dans l'esprit de `proc_windows.go` qui existe déjà ;
4. anglais.

Une valeur inconnue à l'une de ces étapes — `JIGGER_LANG=es` tant que l'espagnol n'existe
pas, `LANG=ja_JP.UTF-8` — n'est pas une erreur : elle retombe simplement sur l'anglais.

La langue est résolue **une fois**, au démarrage. Un processus qui vit huit millisecondes
n'a pas besoin de changement à chaud — c'est la seule différence de fond avec Cocktails, où
le `Localizer` notifie ses liaisons XAML.

**Conséquence à assumer :** un poste dont le shell tourne en `LANG=en_US.UTF-8` — c'est le
cas de la machine de développement — verra jigger en anglais dès la bascule. `JIGGER_LANG=fr`
rétablit le français.

## §4 — Les greffons

**Le message le plus important d'un greffon ne peut pas venir du binaire.** « binaire
introuvable dans le `PATH` » s'affiche précisément quand il n'est pas là ; « le binaire est
en 0.7.0, or ce greffon en demande 0.8.0 » s'affiche quand il est trop vieux — donc trop
vieux pour connaître une commande qui servirait les traductions.

Les six chaînes concernées (deux côté zsh, quatre côté PowerShell) sont donc **autonomes**,
écrites en clair dans chaque greffon, choisies par un `case` sur la langue résolue. À ce
volume, un mécanisme importé coûterait plus cher qu'il ne rapporterait.

La langue s'y résout comme dans le binaire : `JIGGER_LANG`, puis `$LANG`/`$LC_ALL` côté zsh,
`[CultureInfo]::CurrentUICulture` côté PowerShell.

**Le greffon zsh exporte `JIGGER_LANG` s'il le trouve posé.** Les réglages de jigger se
posent sans `export` (`JIGGER_ROWS=12` avant le `source`) parce que le greffon les lit
lui-même ; mais celui-ci doit atteindre **le binaire**, sans quoi le popup parlerait une
autre langue que les messages du greffon. L'habitude de l'utilisateur reste la même, et la
langue est cohérente partout. Côté PowerShell, `$env:JIGGER_LANG` est déjà une variable
d'environnement : rien à faire.

## §5 — La documentation

| Fichier | Après |
|---|---|
| `README.md` | anglais (l'original) |
| `README.fr.md` | français (traduction) |
| `docs/getting-started.md` | anglais |
| `docs/fr/getting-started.md` | français |
| `CHANGELOG.md` | **anglais seul** |
| Description et topics du projet GitLab | anglais |
| ADR, specs, plans, journal, commits, issues | français, inchangés |

Chaque paire porte en tête un renvoi vers l'autre langue.

L'asymétrie de rangement — `README.fr.md` à la racine, mais `docs/fr/getting-started.md` dans
un sous-dossier — n'en est pas une : un README doit rester à la racine pour que GitLab et
GitHub l'affichent, tandis que la documentation gagne à se ranger par langue dès qu'elle
compte plus d'un fichier.

**Le CHANGELOG reste en anglais seul**, et c'est la seule asymétrie assumée : le traduire à
chaque version est un engagement perpétuel, pour un fichier que personne ne relit deux fois.

**Volume** : 1 416 lignes, environ 10 800 mots.

**Une dépendance d'ordre en découle** : le README et le guide contiennent des **captures
réelles** du cadre (`⇥ insérer ↓ parcourir ^G fermer`) et de sorties de la façade. La
documentation anglaise doit montrer des captures anglaises. Traduire avant que le binaire
sache parler anglais obligerait à repasser sur chaque bloc.

## §6 — Tests et non-régression

**La garantie centrale :** à `JIGGER_LANG=fr`, la sortie de `jigger render` est **identique
octet pour octet** à celle d'avant le chantier. C'est le filet déjà utilisé pour la façade —
952 combinaisons de ligne, largeur, profil couleur et focus, comparées entre l'ancien et le
nouveau binaire. Zéro différence, ou le travail n'est pas fini.

**Tous les tests posent `JIGGER_LANG` explicitement** : `t.Setenv` côté Go, l'environnement
du `zpty` côté zsh, celui de `pwsh` côté PowerShell. Sans cela, `tests/zpty.zsh` et
`tests/smoke.ps1`, qui cherchent des chaînes précises (« annuler », « filtrer… »),
passeraient ou échoueraient selon la locale de la machine qui les lance.

**Deux tests neufs :**

- les règles de repli — clé absente rendue telle quelle, traduction vide repliée sur
  l'anglais ;
- aucune entrée anglaise vide dans la table. L'anglais est l'original : il ne se replie sur
  rien.

## Ordre de travail

Cinq étapes, chacune vérifiable seule.

1. **La mécanique et le déménagement.** `internal/i18n`, et les chaînes françaises
   actuelles déplacées dans la colonne FR. **Aucun changement visible** : la
   non-régression octet pour octet le prouve.
2. **La colonne anglaise**, et l'anglais par défaut.
3. **Les greffons** — six chaînes, et l'export de `JIGGER_LANG` côté zsh.
4. **La traduction rétroactive de la documentation**, captures régénérées en anglais.
5. **Le site** — chantier suivant, sur du contenu enfin stable.

## Non-buts

Ce que cette phase ne fait **pas**, et qu'il ne faut pas ajouter en chemin :

- **pas de changement de langue à chaud** — un CLI n'en a pas l'usage ;
- **pas de fichiers de traduction externes** (JSON, PO, `go:embed`). Si un traducteur les
  réclame un jour, la conversion depuis la table est mécanique ;
- **pas d'espagnol ni d'allemand** — les colonnes existent, vides ;
- **pas de pluriels, de genres ni de formats ICU.** Les chaînes de jigger sont courtes et
  sans accord ; ajouter une bibliothèque de pluralisation pour zéro cas serait du poids
  mort ;
- **pas de traduction des sorties des gestionnaires.** `winget` répond déjà dans la langue
  du système, et jigger sait la découper (jeux d'essai français dans
  `internal/winget/testdata/`). Ce chantier ne touche pas à cette lecture ;
- **pas de localisation des dates ni des nombres** — jigger n'en affiche pas.

## Risques

| Risque | Parade |
|---|---|
| La documentation française décroche de l'anglaise | Une seule paire de documents, et le CHANGELOG hors périmètre. Le jour où le français n'est plus tenu, il vaut mieux le retirer que le laisser mentir |
| Un test dépend de la locale de la machine | Tous posent `JIGGER_LANG` ; c'est vérifiable d'un `grep` |
| Une chaîne oubliée dans le code | La clé s'affiche telle quelle, donc visible à l'œil dès le premier essai |
| Les captures de la documentation vieillissent | Elles sont régénérées à l'étape 4, après la bascule, pas avant |
| Traduire une chaîne lue par une machine | §1 en fait un contrat écrit ; la non-régression octet pour octet l'attrape |
