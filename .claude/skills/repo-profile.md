## Build & test
- **Build:** `make build` — `go build -ldflags "-X main.build=$(SHA)" -o jigger[.exe] .`
  (le SHA n'est injecté que pour un binaire compilé ici ; une release n'y passe pas)
- **Full test:** `make test` → `go test ./...`
- **Full test + harnais shell:** `make test-all` → `test` + `$(TEST_SHELL)`, qui vaut
  `test-shell` (zsh) sous Unix et **`test-shell-ps test-pty`** (pwsh) sous Windows
- **Single-suite filter (per-task, fast):** `go test ./internal/<paquet>/...`
  — ou `go test -run '<NomDuTest>' ./...` pour un test isolé
- **Format/lint apply:** `gofmt -w .`
- **Format/lint verify (the gate):** `go vet ./...` (+ `gofmt -l .` doit ne rien lister)
- **Prerequisites / caveats:**
  - **Go 1.26.5 ou plus récent** — la version de `go.mod`, pas celle de la distribution.
  - **`gofmt -w .` dans un clone antérieur à `*.go text eol=lf`** (`.gitattributes`) réécrit
    les 111 fichiers du dépôt en LF sans que `git status` n'en montre rien, l'index étant déjà
    en LF. Si `gofmt -l .` signale tout le dépôt, c'est ce cas : reposer l'arbre avec
    `git rm --cached -r :/ && git reset --hard` sur un arbre propre, **pas** `gofmt -w .`.
    Voir CONTRIBUTING.md, « Ce que le code attend ».
  - `make test-golden` **n'est pas dans `test-all`** et se lance à la main : sa référence dépend
    de la machine, de la version affichée dans la bannière et du catalogue Homebrew local.
    `--capturer` avant un chantier de rendu, `--verifier` après.
  - Les harnais shell demandent `pwsh` (Windows) ou `zsh` (Unix) ; `test-pty` est lent
    (quelques secondes par cas, le temps qu'un pwsh démarre) mais c'est le seul juge de ce que
    l'utilisateur voit du popup.
  - **Un test ne doit jamais dépendre de ce qui est installé sur la machine qui le lance** : un
    test qui ne passe que là où Homebrew existe est un test cassé. `internal/complete` montre la
    manière de s'en sortir.

## Integration style
- **Merge mode:** **merge** — vérifié via l'API : `"merge_method":"merge"`,
  `"squash_option":"default_off"`. Le log le confirme (`Merge branch 'X' into 'main'`).
  **Ne pas écraser (squash)** : ce dépôt garde les commits de la branche.
- **Source branch:** supprimée automatiquement à la fusion (`remove_source_branch_after_merge: true`).
- **MR title convention:** pas de Conventional Commits, pas de gate sémantique. Les titres sont des
  **phrases françaises descriptives** au présent, souvent sans préfixe — p. ex. « L'écran de
  configuration se quitte sans enregistrer », « Un binaire compilé ici s'annonce comme tel ».
  GitLab appose parfois la référence de MR en fin de sujet : `(!43)`.
- **Branch naming:** `<type>/<slug-français>` sans numéro d'issue — `feat/plugin-git`,
  `fix/ps-touches-reprises`, `docs/personnalisation-claude-code`.

## Conflict hot-spots (merge-with-main resolutions)
| File | Why it collides | Resolution |
|------|-----------------|------------|
| `main.go` (`var version = "…"`, l. ~50) | chaque release bump la version | prendre la **plus haute** |
| `CHANGELOG.md` | tout le monde y ajoute une section | **union** |
| `internal/i18n/catalogue.go` | deux branches ajoutent chacune leurs clés | **union** (garder les deux jeux de clés ; vérifier `nbLangues` inchangé) |
| `go.sum` | churn de dépendances | **régénérer** (`go mod tidy`), ne jamais fusionner à la main |
| `README.md`, `README.fr.md`, `docs/` | les fonctionnalités parallèles se documentent | **union** — et les deux README doivent rester d'accord |
| `internal/*/testdata/*`, `tests/captures/*` | sorties réellement capturées | **régénérer** en recapturant ; `.gitattributes` les marque `-text`, **aucune normalisation de fins de ligne** ne doit être introduite en résolvant |
| `docs/media/out/*` | binaires (GIF, images) | **régénérer** (`make media`), jamais de diff textuel |
- **Rule of thumb:** union pour l'additif, régénération pour le dérivé, la plus haute pour la
  version ; même logique des deux côtés = vrai conflit sémantique — comprendre les deux intentions
  ou s'arrêter.

## Architecture grain / invariants (shape implementation plans to these)
- **i18n, non négociable :** toute chaîne visible par l'utilisateur vit dans
  `internal/i18n/catalogue.go`, en **anglais et en français**, une ligne par clé. Une chaîne
  visible absente du catalogue **n'est pas acceptée** (CONTRIBUTING.md). Une traduction manquante
  retombe sur l'anglais, jamais sur un blanc ou une clé brute. Ajouter une langue = élargir la
  table *et* la constante `nbLangues` — voir `docs/specs/2026-08-16-i18n-design.md`.
- **jigger n'exécute jamais `ssh`** : il complète la ligne que l'utilisateur lancera lui-même, et
  reste en dehors du chemin d'exécution. Même esprit ailleurs : il rend la main.
- **Les décisions structurantes sont écrites** : 11 ADR dans `docs/adr/`, les conceptions dans
  `docs/specs/`. Avant de concevoir, lire ce qui a déjà été tranché — c'est explicitement ce que
  CONTRIBUTING.md demande. Une décision structurante nouvelle appelle un ADR (skill `adr`).
- **Découpage par paquet** dans `internal/` : un gestionnaire de paquets = un paquet (`brew`,
  `scoop`, `winget`, `pacman`), plus les transverses `complete`, `config`, `elevate`, `facade`,
  `i18n`, `managers`, `plugin`, `pm`, `prompt`, `ssh`, `ui`. Un nouveau gestionnaire se branche
  par la **façade déclarative** (ADR-0002), pas par des `if` dispersés.
- **Portée assumée :** ADR-0010 fixe le périmètre des gestionnaires de paquets — ne pas l'élargir
  sans le rouvrir.
- **Les tests ne dépendent pas de la machine** (voir *Build & test*).
- **Ne jamais pousser sur le miroir GitHub** : tout commit y serait écrasé à la synchronisation.

## Worktree home
- `.claude/worktrees/` — **ignoré, et c'est un fait du dépôt** : la règle `/.claude/worktrees/`
  est dans le `.gitignore` commité, donc elle vaut sur toutes les machines. `implement-issue` et
  `merge-pr` peuvent y créer un worktree sans risque qu'un `git add -A` égaré le mette en scène.
- `.superpowers/` et `.claude/settings.local.json` sont ignorés par le même fichier.
- **Nuance :** `worktrees-ignored.sh` conclut « ok » mais ajoute « rule source unknown », faute de
  `rev` sur ce Git Bash Windows (`line 120: rev: command not found`) — il n'a donc pas pu montrer
  *d'où* vient la règle. Ne pas lire cet aveu comme un doute sur `.claude/worktrees/` : le
  `.gitignore` tranche. En revanche `.worktrees/` (à la racine, sans `.claude/`) n'y figure pas —
  si un outil le propose comme emplacement, son ignore n'est **pas** garanti hors de ce checkout.

## Environment gotchas
- **Windows + Git Bash :** `rev` n'existe pas ici et casse `worktrees-ignored.sh` (ci-dessus).
  D'autres outils POSIX peuvent manquer de la même façon — ne pas lire une erreur d'outil absent
  comme un verdict.
- **`gh` est installé et authentifié** (v2.98.0) mais vise **github.com**, donc le *miroir*.
  L'utiliser pour les issues/MR de ce projet ouvrirait le ticket au mauvais endroit, sur un dépôt
  public. Toujours `glab`, toujours `-R yves/jigger`.
- **`glab repo create` vise gitlab.com par défaut**, quel que soit l'hôte de connexion : poser
  `GITLAB_HOST=gitlab.yg-devworks.com` pour toute commande lancée hors de ce dépôt.
- **Le miroir est public.** Tout ce qui entre dans `main` est visible d'Internet à la
  synchronisation suivante, irréversiblement.
- **Release :** ne pas créer la release à la main, le job `release:` s'en charge au tag et tire ses
  notes du `CHANGELOG.md`. `GITHUB_RELEASE_TOKEN` doit exister *et* être valide avant de taguer.
  Détails et pièges dans `.claude/forge.md`.
